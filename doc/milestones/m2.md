# M2：Approval Rules + Network Policy

## 当前状态

**Complete（2026-08-20）。** `@aezy/security` 已作为普通外置插件进入真实 Aezy / DSH `0.1.0-rc.8` profile。它没有修改 `.local/deepseek-harness/`，也没有替换 DSH 的 approval、sandbox、tool runtime 或 Web 内核。

M2 补齐四个闭环：

- global / repository 两级持久 Approval Rules；
- 独立于 filesystem sandbox 的 Network Policy；
- Security conversation view 中的设置、规则列表/撤销和近期审计；
- 在 DSH 公开执行 seam 上的真实 ask / deny / allow 判定与原生 one-shot approval 组合。

## 执行边界与组合语义

策略在 `tools/pre-execute` 的 prepend listener 中读取不可变 `ToolExecution`：工具名、解析后的参数、Agent Session、call id 和 Session cwd 都在此时可用。Aezy 先分类、判定并持久化策略相关审计，再把允许结果交给下游 waterfall；因此 Aezy allow 不会跳过 DSH sandbox 或其他插件的 deny/ask。额外的 `tools.guard()` 只做单调 deny backstop，后续 listener 无法把它重新变成 allow。

规则顺序固定为：

1. 命中的 deny rule；
2. 对 `possible` / `required` network action 生效的 Network `deny`；
3. 命中的 ask rule；
4. Network `ask`（命中 allow rule 时放行，否则进入 DSH 原生 one-shot approval）；
5. 命中的 allow rule；
6. 不涉及网络的本地 action 默认允许。

这意味着 Network `deny` 不能被持久 allow rule 绕过。Network `ask` 可以通过精确工具规则或简单 shell 命令前缀持久放行；allow 前缀只匹配单条、无 shell composition/expansion 的 token prefix，绝不授权 `&&`、管道、重定向、命令替换或变量展开。deny/ask 优先于 allow。

Repository scope 通过 Session cwd 向上发现最近的 `.git` 目录或 worktree `.git` 文件，再 realpath canonicalize。没有 Git root 时，以 canonical cwd 作为 project boundary。

## Network Policy 的准确能力边界

默认值为 `ask`，支持 global default 和 repository override：

- `required`：`web_*` / HTTP / browser / MCP / GitHub / GitLab 类工具；`curl`、`wget`、`ssh`、package install/publish、`git fetch/pull/push/clone` 等明显网络 shell；
- `possible`：无法安全解析的 shell、未知可执行文件，以及不在 Aezy 已知本地工具集合中的外置工具；
- `none`：DSH/Aezy 已知本地文件、Git read、Agent bookkeeping 工具和一组保守 shell read 命令。

未知外置工具按 `possible` 处理，所以名称不含 `mcp` 的第三方 MCP tool 也不会在 `ask`/`deny` 下静默穿透。未知 shell 同理。代价是首次运行新的本地工具或 build/test 命令可能询问一次；用户可按 tool 或简单 command prefix 建立 repository/global allow rule。

这是 Agent tool boundary，不是 Linux namespace、防火墙或操作系统级 egress sandbox。DSH 的 model-provider、Session transport 和 control-plane 流量必须保持可用，因此不受此插件拦截；用户自己在 Integrated Terminal 或 Aezy Web 外启动的进程也不在范围内。产品不会把 filesystem sandbox 谎称为网络隔离。

## 持久化、解释与审计

默认状态文件是 `$DSH_HOME/aezy/security.json`，目录权限 `0700`、文件权限 `0600`，通过同目录临时文件 + rename 原子替换。上限为 128 条规则和 500 条审计；损坏或未知格式会阻止插件启动，不会静默重置成宽松策略。载入后的内存状态递归冻结，每次 mutation 都 clone、校验并原子提交。

每条决策记录包含 Session/Turn/call id、canonical repository root、tool、network classification、decision、source、匹配 rule id 和人类可读 explanation。Shell 只保存最多 240 字符的脱敏 preview 与完整命令 SHA-256：URL credentials、常见 TOKEN/KEY/SECRET/PASSWORD 环境变量和 token/password CLI 参数不会原样落盘。DSH 的 `approval/asked` / `approval/decided` 事件会把 `allowed-once`、rejected、cancelled 或 unavailable 结果回填到对应 Aezy ask 审计。

M1 的 Web revert/Undo 是用户直接点击并已有 receipt/fingerprint 门禁，不再重复弹一次 Agent approval；成功后会通过同一个 `aezySecurity` service 记录 `user-confirmation` allow 审计。这样安全写操作与 Agent policy 在一个 Security projection 中可见，同时不把“用户已明确点击”误当成 Agent 持久授权。

## 明确不包含

M2 不实现操作系统级网络 namespace/firewall、用户 Integrated Terminal 策略、Remote/Cloud environment policy、自动安全 reviewer 或第二套 approval UI。M3 Worktree/Handoff 应复用 `aezySecurity` service，并在 environment create/remove/handoff 上加入同类审计。
